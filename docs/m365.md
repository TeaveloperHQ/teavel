# 학교 Microsoft 365 구성

학교의 M365 그룹·Teams를 정리하고 구성한다. **대상은 학교의 M365 관리자** —
대개 전문가가 아니라 그 역할을 떠맡은 선생님이다.

일반 교사용이 아니다. 그룹·팀을 만들려면 전역 관리자 권한이 필요하고,
일반 교사는 애초에 할 수 없는 일이다.

---

## 정한 것과 그 이유

### ① Graph를 기본으로 쓰지 않는다

`Microsoft.Graph` PowerShell은 **"Microsoft Graph Command Line Tools"** 라는 앱으로 붙는데,
`Group.ReadWrite.All` 같은 권한은 **관리자 동의가 필수**다. 학교마다 관리자가
낯선 이름의 앱에 넓은 권한을 승인하는 화면을 봐야 한다는 뜻이다 —
잘 모르는 관리자에게 최악의 첫 화면이고, 무서워서 거부하거나 아무 생각 없이 승인하게 된다.

반면 **`MicrosoftTeams` · `ExchangeOnlineManagement` 는 마이크로소프트 자체 모듈**이라
모든 테넌트에 이미 동의돼 있다. 전역 관리자면 동의 화면 없이 그냥 붙는다.
팀·M365 그룹·구성원은 전부 이 둘로 된다.

| 만들 것 | 모듈 | 동의 |
|---|---|---|
| Teams 팀 | `MicrosoftTeams` | 필요 없음 |
| M365 그룹 | `ExchangeOnlineManagement` | 필요 없음 |
| 구성원 | 같은 모듈들 | 필요 없음 |
| **Entra 보안 그룹** | Graph | **필요함 → 고급으로 뺌** |

보안 그룹만 Graph가 필요해서 **고급**으로 뺐다. 트리에 보안 그룹이 없으면
Graph는 아예 로드하지 않는다. (실제 운영에서도 보안 그룹은 손으로 만들어 왔다)

> 참고: 2025년 말부터 Exchange·Teams API에 대한 기본 동의 정책이 강화돼
> **서드파티** 앱은 관리자 동의가 필요해졌다. 자체 모듈을 쓰는 이 방식은 그 변화도 피해 간다.

### ② SDS를 감지하지 않는다 — 재고부터 본다

처음에는 SDS(School Data Sync)가 만든 그룹을 감지해 갈래를 나누려 했다.
감지는 가능하다 — SDS 확장 특성(앱 ID `fe2174665583431c953114ff7268b7b3`)이나
Graph의 `educationClass.externalSource = "sis"` 를 보면 된다.

**그런데 재고부터 보면 그 갈래 자체가 사라진다.**

무엇이 그것을 만들었든(SDS·손·다른 도구·전임 관리자) 할 일은 같다 —
**이미 있으면 안 만든다.** 원인은 미리보기를 보면 관리자가 안다.

감지를 넣지 않는 이유:

- 감지하려면 Graph 권한이 필요하다(위 ①과 충돌)
- 마이크로소프트가 SDS를 이미 한 번 갈아엎었다(Classic 종료, 팀 생성 기능이 빠졌다 돌아옴).
  표식에 기대면 그 변화에 또 끌려다닌다
- 재고 대조는 모든 원인을 덮는다

### ③ SDS를 쓰지 않는다

| | SDS | PowerShell (이 방식) |
|---|---|---|
| 명단 출처 | SIS → v2.1 규격 CSV | 아무 엑셀이나 |
| 학기 중 변경 | 자동 반영 | 다시 돌려야 함 |
| 초기 설정 | 무겁다 | 없음 |
| 통제권 | 규격이 정하는 대로 | 원하는 모양 그대로 |

**나이스(NEIS) 커넥터가 없다.** SDS의 최대 장점인 자동 동기화가 값어치 있는 건
SIS가 직결될 때인데, CSV를 손으로 만들어 올려야 한다면 그 일이 결국 남는다.
그럴 거면 엑셀에서 바로 PowerShell로 가는 게 짧다.

SDS가 이기는 지점(학기 중 명단 변동)은 **구성원 수렴**으로 메운다 —
"명단 갱신하고 다시 돌리기"가 한 번의 명령이 되게 한다. (아직 미구현)

### ④ 삭제보다 이름 변경이 먼저다

학교엔 지난 몇 년치 그룹이 어질러져 있다. 새 체계를 만들기 전에 그걸 정리해야 하는데,
**지우고 다시 만들면 파일·대화·팀이 전부 날아간다.** 이름만 바꾸면 내용을 그대로 두고
새 체계에 편입시킬 수 있다.

그래서 순서가 이렇다: **재고 보기 → 지울지 / 이름 바꿔 살릴지 결정 → 없는 것 만들기**

표시 이름과 별칭은 분리해 다룬다. 표시 이름만 바꾸면 안전하지만,
**별칭을 바꾸면 메일 주소가 바뀌어** 기존에 공유된 주소로 오던 메일이 끊긴다.

## 흐름

```
① 대조    선언(트리) vs 테넌트 재고 → 계획
② 미리보기 만들 것 · 건너뛸 것 · 확인이 필요한 것을 이름까지
③ 확인    관리자가 승인해야 진행
④ 적용    없는 것만 만든다. 있으면 건드리지 않는다(여러 번 돌려도 안전)
⑤ 보고    만든 것 · 건너뛴 것 · 실패한 것을 각각
```

명령형("팀 24개 만들어")이 아니라 **선언형**("이 학교는 이런 모양이어야 한다")이다.
중간에 끊겨도 다시 돌리면 되고, 이미 있는 걸 덮어쓰지 않는다.

## 구조

```
catalog/m365-tree.json          학교 구조 선언 — 학교마다 이것만 바꾼다
src/Teavel.Core/M365/
  SchoolTree.cs                 읽기 · 펼치기 · 검증
  TreeReconciler.cs             재고 대조 → 계획
scripts/Teavel.M365.psm1        준비확인 · 연결 · 재고 · 이름변경 · 삭제
```

**판단은 전부 C#에 있고 PowerShell은 얇다.** 테넌트가 없어도 로직을 검증할 수 있어야 하기 때문이다.
PowerShell이 하는 일은 "목록 가져오기 / 하나 만들기 / 하나 고치기" 뿐이다.

### 트리 선언

`generate` 를 두면 곱집합으로 펼쳐진다.

```json
{ "id":"class", "kind":"team", "template":"educationClass",
  "displayName":"{학년}학년 {반}반", "mailNickname":"class-{학년}-{반}",
  "generate": { "학년":[1,2,3], "반":[1,2,3,4,5,6] } }
```

→ 18개 팀. `kind` 는 `security` · `m365` · `team`.

## 실제 학교 테넌트에서 배운 것

작은 테넌트(그룹 11개) 하나를 열어 봤다. 거기서 나온 것들이 설계를 바꿨다.

### 별칭은 믿을 수 없다 — 대조는 이름으로

한글 이름으로 그룹을 만들면 별칭에서 뜻이 날아간다.

```
3학년_4반     →  3_4                 한글이 빠짐
3학년_과학     →  3_                  '과학' 이 통째로 사라짐
늘푸른 학생회   →  msteams_83a1ec      Teams 가 자동 생성
제주도 여행     →  949                 숫자만 남음
```

그래서 두 가지가 정해진다.

- Teavel 이 만들 때는 `mailNickname` 을 **영문으로 반드시** 받는다(이미 강제하고 있다).
- 기존 그룹과 대조할 때는 **표시 이름**을 기준으로 삼는다. 별칭은 보조일 뿐이다.

### 'All Company' 는 건드리면 안 된다

테넌트를 만들면 자동으로 생기는 조직 전체 그룹인데, **동적 그룹이라 구성원이 0명으로 온다.**
"구성원 없음 → 정리 후보" 로 넘기면 지우면 안 되는 것을 지우라고 권하게 된다.
별칭이 `AllCompany.<숫자>.<임의문자>` 꼴인 것으로 알아본다 — 이름은 테넌트 언어에 따라 달라진다.

### 정리 후보는 이름 생김새와 사람 수로 가른다

실제 테넌트에는 수업 그룹(30명·203명)과 시험용 잔재(`Test` `TEST` `테스트` `히히`, 1~2명)와
개인 그룹(`제주도 여행`)이 섞여 있었다. 관리자가 알고 싶은 것은 "무엇을 지워도 되나" 이고,
그 재료는 **이름의 생김새와 사람 수** 두 가지다.

`InventoryTriage` 가 셋으로 나눈다 — 쓰이는 것 / 정리 후보 / 건드리면 안 되는 것.
지우지는 않는다. 판단은 관리자가 하나씩 한다.

### 모듈 설치가 진짜 관문이다

실제 교사 PC(Windows 11 Pro 25H2, PowerShell 5.1)에서 EXO 모듈을 올리려다 다섯 겹에 걸렸다.

| 관문 | 증상 |
|---|---|
| TLS SystemDefault | 갤러리 연결 실패 |
| PSGallery Untrusted | "정말 하시겠습니까?" 에서 멈춤(비대화형이면 영영) |
| PowerShellGet 1.0.0.1 | 낡아서 `-Force` 가 안 먹는 구석이 있다 |
| PackageManagement 사용 중 | 갱신이 막힌다 — 새 프로세스가 필요 |
| **OneDrive 문서 폴더** | 폴더 백업이 켜져 있으면 모듈 경로가 `OneDrive\문서\` 로 간다 |

마지막 것이 특히 한국 학교에서 흔할 것이다. 경로를 짐작하면 반드시 틀리므로
**`$env:PSModulePath` 를 읽어야 한다.** 그리고 OneDrive 아래에 모듈을 두면
파일 온디맨드로 DLL 이 자리표시자가 되어 어셈블리 로드가 실패할 수 있다.

`Install-TeavelM365Module` 은 "있으면 넘어감" 이 아니라 **최소 버전을 봐야 한다** —
3.6.0 이 깔려 있으면 그대로 두고 나중에 없는 매개변수에서 터진다.

## 검증 상태

### 리눅스에서 확인한 것 (테넌트 불필요)

`SchoolTree` — 학년×반 18개 펼치기 · `generate` 없을 때 하나만 ·
못 채운 자리표시자 감지 · 한글 별칭 거부 · 별칭/이름 겹침 · `kind` 오타

`TreeReconciler` — 없으면 만들기 · 이미 있으면 건너뛰기 ·
팀 없는 그룹 감지 · 별칭 선점 감지 · 이름과 별칭이 서로 다른 그룹을 가리키는 경우

### 확인하지 못한 것

**만들기·이름변경·삭제.** `Get-UnifiedGroup` 은 실제 테넌트에서 돌려 봤지만
`New-Team` · `Set-UnifiedGroup` · `Remove-UnifiedGroup` 은 아직 한 번도 부르지 않았다.
남의 테넌트를 바꾸는 일이라 시험도 조심해야 한다.

`Get-UnifiedGroup` 이 실제로 주는 것은 확인했다 —
`DisplayName` · `Alias` · `PrimarySmtpAddress` · `WhenCreated` ·
`ResourceProvisioningOptions`(팀 여부) · `GroupMemberCount` · `AccessType` 모두 온다.

## 남은 일

1. **`Teavel.M365.psm1` 실기 검증** — Windows에서 실제 테넌트에 붙여 보기.
   특히 `Get-UnifiedGroup` 의 어떤 속성이 실제로 오는지(`GroupMemberCount`, `AccessType`,
   `ResourceProvisioningOptions`) 확인이 필요하다.
2. **재고 화면 설계** — 그룹이 100개면 하나씩 물을 수 없다.
   실제 학교의 목록이 어떻게 생겼는지 보고 묶는 방식을 정한다.
3. **만들기 구현** — `New-Team` · `New-UnifiedGroup`. 아직 없다.
4. **구성원 수렴** — 명단 엑셀 대비 추가·제거. SDS를 안 쓰는 대가를 치르지 않으려면 필요하다.
5. **보안 그룹(고급)** — Graph 경로. 트리에 보안 그룹이 있을 때만.
